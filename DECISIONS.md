# DECISIONS.md

Framework and library choices made during the v3 rebuild, with rationale.

## Stack

| Layer | Choice | Why |
|---|---|---|
| UI framework | **CustomTkinter 5.2+** | Spec §1.8: no Qt. CTk's footprint is ~5 MB vs PySide6's ~80 MB. |
| DnD | **tkinterdnd2** | Spec §5: only established add-on for Tk DnD. Optional in code (graceful degradation). |
| Dark-mode detection | **darkdetect** | CTk's standard dependency; no separate decision needed. |
| Manifest format | **TOML (tomllib stdlib)** | Unchanged from v2; `tomllib` is stdlib in Python 3.11+, falls back to `tomli` backport on 3.10. |
| Subprocess lib | **stdlib `subprocess.Popen`** | Replaces v2's `QProcess`. Spec §1.1: process-per-run via `Popen`, never in-process. |
| Installer | **Inno Setup 6** | Spec §7 explicitly recommends; simpler than WiX for a single-exe Python app. |
| Bundling | **PyInstaller `--onedir`** | Spec §7: NOT `--onefile` (onefile's temp-unpack-on-every-launch works against the "fast" goal). |

## Architecture decisions

### 1. Two-Pythons invariant (spec §7 — CRITICAL)

The host UI is Python, so PyInstaller necessarily bundles a Python interpreter to run CustomTkinter. That interpreter is **for the UI process only**.

For `.py` tool scripts, `RuntimeResolver._resolve_python()` checks in this order:

1. **System Python on PATH** (`py.exe` / `python.exe` on Windows, `python3` / `python` on POSIX) — preferred, this is the entire point of v3.
2. **`installer/python-embed/python.exe`** — a deliberately-minimal embeddable Python shipped alongside the frozen app as a fallback.
3. **Never** the PyInstaller-bundled interpreter inside `dist/ToolPouch/_internal/`.

To prevent silent regression, `build_subprocess_env()` strips `PYTHONHOME` and `PYTHONPATH` when frozen — those vars would otherwise *force* a system Python to use the frozen app's stdlib, recreating v2's "bundles everything, ignores the PC" problem.

**Verified by**: `scripts/runner_test.py` shows `python_exe: /home/z/.venv/bin/python3` (the system Python on PATH), not the bundled one. The Phase 8 spec checkpoint ("which interpreter actually launched the tool script") is satisfied.

### 2. Worker-thread → queue → `.after()` polling (spec §5 — CRITICAL)

CustomTkinter (like all Tkinter) is **not thread-safe** for widget updates from a background thread. `ToolRunner` reads subprocess stdout on a daemon thread and fires callbacks (`on_log`, `on_progress`, `on_status`, `on_finished`). Those callbacks only `queue.put(...)` items — they **never touch a CTk widget**.

`ToolPanel._drain_loop()` runs every 50 ms on the UI thread via `self.after(50, self._drain_loop)`, drains the queues, and applies the updates to widgets.

The worker thread caps log draining at 200 lines per tick to prevent UI freeze on huge output bursts, and the log textbox caps its buffer at 5000 lines for long-running tools.

### 3. v2 manifest compatibility (spec §2)

The 23 existing v2 tool.toml files use inconsistent formats:
- `type = "File"` (capitalized) vs `type = "folder"` (lowercase)
- `default_value = "..."` vs `default = "..."`
- `options = "a,b,c"` (comma string) vs `options = ["a", "b", "c"]` (array)
- `[[dependencies]] id = "Pillow"` (wrong key) vs `[[dependencies]] import = "fitz"` (correct)
- `min_version = "..."` vs `version = "..."`

`core/tool_loader.py` normalizes all of these at parse time so the UI only ever sees the canonical v3 vocabulary. This is the spec §2 compatibility bar — verified by `tests/test_tool_loader.py::TestV2Compatibility` (all 23 v2 manifests parse without error).

### 4. Multi-ecosystem dependency providers (spec §6)

Each ecosystem has its own provider module under `deps/`:
- **`python_provider.py`** — wraps v2's `core.dependency_checker` (ast-based import scanner) + `pip install`
- **`node_provider.py`** — reads `package.json`, uses `npm install -g`
- **`powershell_provider.py`** — `Get-Module -ListAvailable` / `Install-Module -Scope CurrentUser`
- **`none_provider.py`** — no-op, exists so batch tools have a consistent (empty) row

The Dependency Manager UI aggregates statuses from all providers into a single table with an `Ecosystem` column. Install operations are dispatched to the right provider per-row.

### 5. Theme JSON structure (spec §5)

CTk theme JSON uses `["light_color", "dark_color"]` list form so the same theme file works in both appearance modes. The 5 themes are generated by `scripts/build_themes.py` from a palette dict overlaid on CTk's default `blue.json` structural template (corner_radius, border_width, button_length, etc. preserved unchanged).

**Color roles dropped from v2 (no clean CTk equivalent — flagged per spec §5):**
- `QPalette.ToolTipBase / ToolTipText` — CTk has no tooltip widget
- `QPalette.BrightText` — no bright-text role
- `QPalette.PlaceholderText` — folded into `CTkEntry.placeholder_text_color`
- Per-state alternate row colors — `CTkScrollableFrame` is flat

### 6. Threading for dependency install

The Dependency Manager's "Install all missing" button spawns a worker thread that calls each ecosystem's `install()` (which runs `pip install`, `npm install`, or `Install-Module`). Log output flows back through a `queue.Queue` and is drained by a `.after(100, ...)` loop on the UI thread — same pattern as the tool runner.

### 7. Installer: per-user, no admin required

`PrivilegesRequired=lowest` in `toolpouch.iss` — installs to `%LOCALAPPDATA%\Programs\Tool Pouch` (via Inno's `{autopf}` token), no admin elevation needed. User config lives in `%APPDATA%\.toolpouch\` (well, `~/.toolpouch/` in code; on Windows `Path.home()` resolves to `%USERPROFILE%`).

### 8. Uninstaller preserves user data

The Inno Setup uninstaller removes the app folder (`{app}\tools`, `{app}\assets`, the exe) but **deliberately does NOT** remove `%USERPROFILE%\.toolpouch\` (config.json + logs + favorites). A user reinstalling keeps their settings; a user who wants a full clean deletes that folder manually.

## Non-goals (spec §10 — unchanged from v2)

- No sandboxing / permission system for tool scripts.
- No plugin API beyond TOML manifest + stdout protocol.
- **No cross-platform support** — Windows-only, permanent.
- No cloud sync, telemetry, or auto-update.
- No PySide6/PyQt/ttk shortcuts anywhere.
